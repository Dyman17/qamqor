# esp — прошивка ошейника

Один файл для прошивки: [`qamqor_collar/qamqor_collar.ino`](qamqor_collar/qamqor_collar.ino) (Arduino IDE; тот же файл собирается PlatformIO через `src_dir` в `platformio.ini`). Контракт: [api-contract.md](../docs/architecture/api-contract.md), [device-code-protocol.md](../docs/architecture/device-code-protocol.md).

## Настройка (верх файла `.ino`)

```
#define WIFI_SSID "YOUR_WIFI"
#define WIFI_PASS "YOUR_PASSWORD"
#define DEVICE_CODE "12345678"   // 8 цифр этого ошейника
```

В репозитории лежат только заглушки. **Реальный Wi-Fi вписывается только в `esp/local/qamqor_collar/qamqor_collar.ino`** (папка `esp/local/` в `.gitignore`, не коммитится). После изменений основного файла эту копию нужно пересоздать (скопировать основной файл и вернуть две строки Wi-Fi). Пароль в лог не печатается. `DEVICE_CODE`: ровно 8 цифр, проверяется при старте; тот же код владелец «принимает» в кабинете.

## Подключение (реальное железо владельца)

| Компонент | Вывод | Пин ESP32 |
|---|---|---|
| Вибромотор (модуль) | сигнал | GPIO18 (HIGH = вкл) |
| Активный зуммер (модуль) | сигнал | GPIO19 (HIGH = вкл, без тона) |
| GPS NEO-6M | TX модуля -> RX | GPIO16 (UART2 RX), 9600 бод |
| GPS NEO-6M | RX модуля <- TX | GPIO17 (UART2 TX) |
| Пульс MAX30102 | SDA / SCL | GPIO21 / GPIO22 |
| Динамик MAX98357A | BCLK / LRC / DIN | GPIO26 / GPIO25 / GPIO27 |

I2S: 16 кГц, 16 бит, моно (левый канал), «старый» драйвер `driver/i2s.h`.

## Прошивка: Arduino IDE

1. Boards Manager: «esp32 by Espressif», версия **2.0.x** (собрано на 2.0.17). Ядро 3.x не подходит (другой I2S API).
2. Library Manager: `SparkFun MAX3010x Pulse and Proximity Sensor Library`, `TinyGPSPlus`, `ArduinoJson` (7.x).
3. Откройте `qamqor_collar/qamqor_collar.ino` (для варианта с Wi-Fi: `local/qamqor_collar/qamqor_collar.ino`; папка должна называться так же, как файл).
4. Плата «ESP32 Dev Module», порт, Upload, Serial Monitor 115200.

## Прошивка: PlatformIO

```
pip install platformio
cd esp
pio run                 # сборка
pio run -t upload       # прошивка
pio device monitor      # лог, 115200
```

Если путь пользователя Windows содержит кириллицу, PlatformIO не находит `Arduino.h`: задайте ASCII-каталог ядра, например `PLATFORMIO_CORE_DIR=C:/pio_core`. Для варианта с реальным Wi-Fi временно подставьте его как `src_dir` или используйте Arduino IDE.

## Что делает прошивка

**Ядра.** Пульс (MAX30102), GPS и актуаторы (I2S-динамик, зуммер, вибромотор) работают в `loop()` на ядре 1 без длинных пауз. Сеть работает в отдельной задаче на ядре 0, поэтому HTTP (до 25 с таймаут) не останавливает датчики.

**Пульс.** `IR < 25000` = палец не приложен (сброс среднего через 3 с); `checkForBeat`; принимается BPM 45..190; сглаживание `0.5*avg + 0.5*bpm` (первый замер берётся сразу); среднее сбрасывается в 0, если 4 с нет удара. Нет пульса: в запросе `heartRate: null`.

**Запрос.** `POST https://qamqor-api.onrender.com/api/v1/device/telemetry`, заголовок `X-Device-Code` и `code` в теле. Поля: `timestamp`, `latitude`, `longitude`, `accuracy` (HDOP x 5 м; 999 при потерянном фиксе), `satellites`, `hdop`, `speedKmh`, `signal` (только если RSSI < 0), `heartRate`. Новых полей, которых нет в контракте, прошивка не шлёт (сервер отклоняет неизвестные поля).

**Время.** Пока NTP не синхронизирован, отправка не блокируется: уходит pulse-only тело (без координат, `accuracy` и `timestamp`), чтобы сервер видел ошейник. NTP запускается один раз после подключения Wi-Fi и досинхронизируется в фоне. С синхронным временем в тело добавляется `timestamp` (ISO 8601, UTC, `Z`); координаты уходят, если позиция когда-либо была (при потерянном фиксе это последняя позиция с `accuracy` 999).

**Периодичность.**
- До первого успешного ответа: старт через 5 с; пока Wi-Fi не поднят, проверка примерно каждые 5 с плюс до 8 с ожидания подключения.
- Дальше: `nextInterval` из ответа сервера, зажатый в 1..3600 с (нет поля: 300 с). Сервер возвращает 1 с, пока кто-то смотрит ферму вживую, 30 с для непринятого ошейника, 300 с в обычном режиме, меньше за границей.
- Сеть (status <= 0), 5xx, некорректный ответ, `success:false`, чужой `code`: экспоненциальная пауза 2, 4, 8 ... до 60 с, сбрасывается после успеха.
- 400 и прочие 4xx: 60 с. 401/403: 300 с. 429: `retryAfterSec` из тела, затем заголовок `Retry-After`, затем 60 с; зажато в 5..3600 с.
- Быстрее этих пауз прошивка не повторяет запрос (кроме одного повтора на новом соединении, см. ниже).

**Wi-Fi и соединение.** Wi-Fi: авто-переподключение и `WiFi.reconnect()`; полный `disconnect + begin` только после 3 подряд неудачных проверок (каждая ждёт до 8 с). TLS-соединение держится (keep-alive) только если следующий интервал не больше 15 с; иначе после чтения ответа закрывается. Если запрос на переиспользованном соединении упал с ошибкой соединения (не таймаут), он один раз сразу повторяется на новом соединении. HTTP-таймаут 25 с.

**Ответ.** Принимается, если HTTP 200, `success == true` и `code` равен своему коду; иначе строка в логе и пауза как при ошибке, актуаторы не включаются.

**Актуаторы.** При отсутствии ответа всё выключено: актуатор включается только по свежему ответу и сам гаснет по таймеру.
- Ответ включает актуатор не более одного раза: пока динамик, зуммер или вибромотор ещё работает, повторные ответы его не перезапускают и не продлевают.
- Динамик (`sound` + `toneFrequencyHz`, 100..3000 Гц): 600 мс. Вибрация (`vibrate` + `vibrateDurationMs`, 3000 мс у сервера): указанная длительность. Динамик и зуммер не дольше 5 с на команду.
- Собственный лимит прошивки, независимо от сервера: вибромотор, зуммер и динамик каждый не более 5 с суммарно в скользящем окне 30 с (учёт секундными корзинами, точность около 1 с); при исчерпании текущее включение обрывается, новое не включается (или укорачивается до остатка бюджета). Команда, которую нельзя выполнить (актуатор занят или бюджет исчерпан), пишется в лог как `[cmd] dropped, busy` с типом и id.
- Окно лимитов считается по 64-битному времени `esp_timer` (не переполняется), дедлайны актуаторов сравниваются разностью `uint32_t`, поэтому переполнение `millis()` (около 49 суток) безопасно.
- Независимый сторож (отдельная задача на ядре 0): `loop()` отмечается каждую итерацию; если отметка старше 1 с или актуатор работает дольше своего дедлайна более чем на 150 мс, сторож сам переводит вибромотор и зуммер в LOW и останавливает I2S, а `loop()` при возврате сбрасывает состояние.
- Пины `PIN_VIBRATION` и `PIN_BUZZER` переводятся в OUTPUT LOW первыми в `setup()`, но до этого (загрузчик, сброс) они плавают: рекомендуется подтяжка к земле (pull-down, около 10 кОм) на входах модулей вибромотора и зуммера.
- Команда `command {id, type}`: `TEST_SOUND` и `TEST_SPEAKER` (динамик 1200 Гц, 800 мс), `TEST_BUZZER` (зуммер 500 мс), `TEST_VIBRATION` (1000 мс). Id последней выполненной команды запоминается (только в RAM, теряется при перезагрузке); команда с тем же id игнорируется.
- Необязательные поля ответа `speakerMs`, `speakerHz`, `speakerVolume`, `buzzerMs`, `vibrateMs` разбираются, но **сервер их пока не шлёт**; прошивка применяет их с теми же ограничениями.

**Диагностика.** Не чаще раза в минуту в лог: свободная куча, максимальный свободный блок, запас стека сетевой задачи.

## Корневой сертификат (TLS)

Встроен GTS Root R4 (цепочка `onrender.com` <- Google Trust Services `WE1` <- `GTS Root R4`, проверено 2026-11-09 через `openssl s_client`, корень действует до 2036-06-22). Если связь падает с ошибкой сертификата:

```
openssl s_client -connect qamqor-api.onrender.com:443 -servername qamqor-api.onrender.com -showcerts
```

Замените PEM в `.ino` на новый самоподписанный корень цепочки. Отключать проверку нельзя.

## Что проверено и что нет

- Проверено: сборка `pio run` проходит (ядро 2.0.17, `espressif32@6.9.0`).
- Не проверено на плате: пульс и его пороги, GPS, I2S-динамик, зуммер, вибромотор, лимиты 5 с / 30 с, сторож актуаторов, повтор на новом соединении, обработка 429 и back-off.
- Не проверено с живым сервером: обмен, pulse-only без NTP, дедупликация команд, поведение при `nextInterval` 1 с.
- Громкость динамика (`AUDIO_AMPLITUDE`) и пороги пульса подобраны по описанию, не на железе.
- Пароль Wi-Fi из прежней версии остаётся в истории git; его нужно сменить.

## Протокол с сервером

Запрос `POST /api/v1/device/telemetry` (с синхронным временем и позицией):

```json
{"code":"12345678","timestamp":"2026-11-09T08:15:30Z","latitude":43.65012,"longitude":51.15731,"accuracy":6.5,"signal":-71,"speedKmh":1.2,"hdop":1.3,"satellites":9,"heartRate":64}
```

Без синхронного времени (или без позиции) координаты, `accuracy` и (без NTP) `timestamp` опускаются; `heartRate` — целое или `null` (нет контакта):

```json
{"code":"12345678","signal":-71,"speedKmh":0.0,"satellites":0,"heartRate":66}
```

Ответ 200 всегда содержит тот же `code`, а также `nextInterval`, `sound`, `toneFrequencyHz`, `vibrate`, `vibrateDurationMs`, `zone`, `mode`, необязательный `command` (см. [api-contract.md](../docs/architecture/api-contract.md)). Сервер принимает любой корректный 8-значный код: первый пинг неизвестного кода создаёт «непринятое» устройство (ответ 200, `zone:"UNKNOWN"`, без сигналов); после приёма кода владельцем ошейник работает как обычно.

## Известный риск

8-значный код не секрет: тот, кто знает принятый код, может отправлять ложные позиции. Усиление позже: необязательный секрет или HMAC тела.
